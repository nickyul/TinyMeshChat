# TinyMesh Chat

TinyMesh Chat — настольный P2P-чат с групповыми голосовыми звонками на C++20, Qt 6 и libdatachannel для небольшого динамического mesh. Центрального сервера и signaling-сервера нет: первое offer/answer-соединение с новым участником передаётся вручную строкой `tmc2:` или файлами `.tmcinvite` и `.tmcanswer`, остальные прямые каналы строятся автоматически.

## Что работает

- постоянная локальная identity с UUID;
- создание эфемерного mesh;
- приглашения от любого участника mesh;
- импорт invitation и answer из текста или файла;
- non-trickle ICE и настраиваемые STUN-серверы;
- прямой надёжный WebRTC DataChannel;
- групповой голосовой звонок Opus 48 кГц mono по отдельным прямым WebRTC audio tracks;
- JSON-пакеты `peer.hello`, `chat.message`, `chat.ack`, `voice.state`, `ping` и `pong`;
- эфемерный mesh, roster, сообщения и состояния доставки только в памяти текущего запуска;
- ограниченная RAM-дедупликация сообщений без истории и повторной отправки после реконнекта;
- логические часы Лэмпорта;
- динамический список до 6 участников и автоматическое построение full mesh;
- маршрутизация служебных offer/answer через уже открытые P2P-каналы без передачи текста посредникам;
- отправка сообщения по всем открытым прямым соединениям;
- отображение участников, состояния mesh и количества ACK;
- редактирование STUN и сетевые диагностические сведения в GUI;
- сохранение signaling в файл и копирование в буфер обмена;
- консольная P2P-диагностика;
- автоматическое развёртывание Qt runtime после сборки.

## Требования

- Windows 10/11;
- Visual Studio 2022 с компонентами C++;
- CMake 3.25+;
- Qt 6.5+ с MSVC 2022 x64;
- отдельная установка vcpkg, указанная через `VCPKG_ROOT`.

Локальные пути к Qt и vcpkg задаются в `CMakeUserPresets.json`. В текущих локальных presets используются:

```text
C:\Qt\6.8.3\msvc2022_64
C:\vcpkg
```

## Подключение нового пользователя

1. Любой участник mesh нажимает `Пригласить`.
2. После завершения ICE он отправляет новичку строку `tmc2:` или `.tmcinvite`.
3. Новичок импортирует приглашение и возвращает созданный answer.
4. Пригласивший импортирует answer.
5. Список участников распространяется по открытым каналам, после чего недостающие прямые соединения создаются автоматически.

## Голосовой звонок

После установления прямого соединения любой участник нажимает `Начать звонок`. Остальные увидят значок микрофона рядом с его именем и присоединяются той же кнопкой. `Выключить микрофон` прекращает отправку голоса, а `Выйти из звонка` останавливает локальное аудиоустройство и передачу аудио.

Голос кодируется Opus кадрами по 20 мс и отправляется отдельно каждому участнику full mesh. Сервер, relay, запись звонка и сохранение аудио на диск не используются. На macOS при первом звонке нужно разрешить приложению доступ к микрофону; на Windows доступ регулируется системными настройками конфиденциальности. Для первого теста лучше использовать наушники; встроенное AEC можно включить в настройках аудио, но его результат зависит от устройства и драйвера.

Перед кодированием микрофон обрабатывается WebRTC Audio Processing Module блоками по 10 мс. Доступны AEC, high-pass filter, четыре уровня noise suppression и AGC1 в режиме `AdaptiveDigital` с настраиваемыми target level, compression gain и limiter. Сетевой тракт при этом остаётся 20-миллисекундным: один Opus/RTP-кадр содержит 960 mono samples при 48 кГц. Приём использует адаптивный jitter buffer, Opus FEC и PLC.

Аудиотракт разделён между двумя рабочими потоками. DSP worker выполняет APM, meter/VAD, Opus encode/decode, сведение и playback; `AudioTransportWorker` принимает сырые RTP-пакеты из callbacks libdatachannel и рассылает готовые Opus-кадры по открытым audio endpoints. Кадровые `QByteArray` не проходят через GUI event loop: в UI отправляются только команды, переходы состояния речи и статистика с ограниченной частотой.

Потери считаются по RTP sequence number за двухсекундное окно. Sequence и timestamp разворачиваются с учётом wraparound, reorder и duplicate. Если после VAD/PTT-паузы приходит следующий sequence с новым timestamp, это считается началом нового talkspurt, а не потерей; пустая очередь выдаёт тишину без PLC и роста буфера. FEC/PLC применяется только при подтверждённом пропуске, когда в очереди уже есть пакет с более новым sequence number.

Передачу можно включать по VAD с настраиваемыми порогом и hangover либо системным Push-to-Talk. Для PTT назначается одна клавиша, средняя или боковая кнопка мыши; состояние опрашивается только во время активного PTT-звонка и работает в фоне на Windows и macOS. Зелёный индикатор в списке участников показывает локальную и удалённую речь; удалённое состояние определяется по аудиокадрам и не меняет JSON-протокол.

Кнопка `Слушать микрофон` включает живой мониторинг уже обработанного сигнала. Во время звонка собеседники продолжают воспроизводиться, локальный микрофон добавляется в общий playback, а его исходящая передача временно блокируется, чтобы не создавать обратную связь в разговоре.

## Динамическая сетка

Участники обмениваются `peer.snapshot`. Для каждой отсутствующей пары инициатор детерминированно выбирается по `peer_id`, поэтому встречные offer не конфликтуют. Критичные `link.offer` и `link.answer` распространяются по существующим каналам с TTL и дедупликацией по идентификатору пакета. При лимите 6 на каждом узле может быть до 5 прямых каналов.

Текст чата отправляется только по прямым DataChannel. Пригласивший участник не становится сервером сообщений.

## Данные и конфигурация

В каталоге `QStandardPaths::AppDataLocation` находятся:

```text
identity.json
config.json
```

`config.json` создаётся при первом запуске и содержит список STUN-серверов и настройки аудио. STUN можно изменить через меню `Инструменты → Настройки STUN`; новые значения применяются к новым соединениям. Сетевые таймауты и лимит участников задаются встроенной политикой приложения.

Аудионастройки включают устройства capture/playback, параметры WebRTC APM, громкость и bitrate Opus, режим `voice_activity|push_to_talk`, параметры VAD и платформенную PTT-привязку. Старые конфиги без этих полей продолжают загружаться со значениями по умолчанию в памяти и не переписываются при запуске; полная нормализация выполняется при следующем успешном пользовательском сохранении.

Сохранение аудионастроек транзакционное: сначала проверяется draft и применяется runtime-конфигурация, затем весь актуальный `AppConfig` атомарно записывается через `QSaveFile`. Ошибка применения не меняет config, а ошибка записи запускает откат аудиодвижка; controller и PTT-привязка обновляются только после успеха обоих шагов.

После перезапуска приложение не восстанавливает mesh, roster, сообщения или состояния доставки: нужно создать новый mesh либо импортировать свежее приглашение. Новый участник видит только сообщения, полученные после подключения. На диск записываются только стабильная identity и пользовательские настройки.

При обрыве не создавайте новый mesh. Любой доступный участник может создать новое приглашение; после восстановления первого канала остальные связи снова достроятся автоматически.

TURN и relay не используются. Поэтому соединение может не установиться при симметричном NAT, некоторых вариантах CG-NAT, блокировке UDP или корпоративном firewall.

Если одна из пар в mesh не достраивается, откройте `Инструменты → Диагностика сети`. В логе события `mesh_signaling` показывают origin/receive для `link.offer` и `link.answer`, а секция ICE — найденные кандидаты и выбранную пару. Наличие только `host`-кандидатов обычно указывает на недоступный STUN; повторяющийся ICE failure при наличии `srflx` чаще означает несовместимый NAT или firewall, для которого без TURN прямого пути нет.

## Portable-пакет

Windows x64 job запускает `scripts/package-windows.ps1`. Скрипт создаёт `dist/TinyMeshChat.zip` с Qt runtime и полной DLL-цепочкой libdatachannel, проверяет обязательные DataChannel/ICE/SRTP/OpenSSL/Opus/Abseil библиотеки, выполняет console и offscreen QML smoke с timeout и только затем проверяет и публикует архив. WebRTC APM линкуется статически и отдельной DLL не требует.

## Сборка на macOS

macOS arm64 job с deployment target 12 использует Xcode, CMake, Ninja, Qt 6.9.3 и статические vcpkg-зависимости, после чего запускает `scripts/package-macos.sh`. Скрипт запускает `macdeployqt`, выполняет ad-hoc подпись и strict verification, console/offscreen QML smoke с timeout, проверяет arm64 у Mach-O-файлов и отсутствие ссылок на build tree, после чего создаёт и проверяет `dist/TinyMeshChat-macOS.zip`.

На другом Mac распакуйте ZIP и запустите `TinyMeshChat.app`. Поскольку сборка не подписана сертификатом Apple Developer ID и не notarized, при первом запуске может потребоваться команда `Открыть` из контекстного меню Finder.

Workflow `Desktop builds` запускается вручную, для push в `main` и pull request в `main`. Он собирает ARM64-архив `TinyMeshChat-macOS.zip` и portable `TinyMeshChat.zip` для Windows 10/11 x64. Оба архива можно скачать на странице GitHub `Actions` из раздела `Artifacts` соответствующего запуска.
